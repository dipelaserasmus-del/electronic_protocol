# B08 — Protocol numbering race (concurrent users)

| | |
|---|---|
| Status | ✅ Fixed |
| Branch | `task/B08-numbering-race` |

## The problem
The next number was computed as "highest number of the year + 1" and then inserted, with nothing
preventing two requests from doing this at the same moment. Both got the same number; the database's
unique key (number + year) rejected the second insert. The user then saw *«Υπήρξε κάποιο πρόβλημα
στην καταχώριση… επαναλάβετε»* and was sent to an **empty** new-protocol form: what they had typed was lost.
The same race existed in email registration.

## Measured before the fix
`tests/concurrency/parallel-save.sh 20` — 20 logged-in sessions press "save" at the same moment:

```
Requests sent:        20 (all proposing the same next number)
HTTP results:              20 302 
Redirected to saved protocol: 15
Redirected with error:        5
Protocols actually stored: 15 of 20 (5 users lost their entry)
```

## Fix
- `App\Services\ProtocolNumbering::create()`: number allocation **and** insert run under a MySQL
  advisory lock (`GET_LOCK`), inside a transaction. Requests queue for a few milliseconds instead of colliding.
- Defence in depth: if a duplicate still happens (e.g. a process that doesn't take the lock), it retries
  with the next number (automatic numbers) or returns to the form with a clear message (manual numbers, B03).
- Used by both the protocol form and **email registration**; the "new protocol" form shows the same next number.
- On any other save error the form now comes back **with the user's input** instead of an empty form.

## Measured after the fix
```
Requests sent:        20 (all proposing the same next number)
HTTP results:              20 302 
Redirected to saved protocol: 20
Redirected with error:        0
Protocols stored: 20 of 20, 20 distinct consecutive numbers (793–812)
```
Heavier run with 50 simultaneous saves:
```
Requests sent:        50 (all proposing the same next number)
HTTP results:              50 302 
Redirected to saved protocol: 50
Redirected with error:        0
Protocols stored: 50 of 50, 50 distinct consecutive numbers (813–862), no gaps
```

## Automated tests (64 tests / 188 assertions pass)

| Test | Asserts |
|---|---|

| `manual_number_taken_at_save_time_raises_specific_exception` | manual numbers are never silently changed |

## Notes
- Re-run the measurement yourself: `./dev.sh up`, then `tests/concurrency/parallel-save.sh 20`.
- Saves are serialised only for the few milliseconds of number allocation; the slower parts
  (file uploads, emails) happen outside the lock.
