# F10: Docker image: security updates from the main archive when security.ubuntu.com fails

| | |
|---|---|
| Status | ✅ Done |
| Branch | `task/F10-apt-security-fallback` |

## What was wrong
On 2026-11-25/26 Ubuntu published a security update of `libtiff6`. For hours afterwards, half of the
security.ubuntu.com servers (91.189.91.82 and .83) still answered **404** for the file, while the index already
listed it; the other two (185.125.190.82 and .83) had it. Which server answers is chosen at random, so about every
other image build failed. This hit CI's *Docker image builds*, the arm64 build and the *Browser tests* (which build
the stack), on #145, #149, #151 and on `master`. F09's retries do not help with a 404: the same server answers the
same.

## What changed
`Dockerfile`: the packages are installed as before. **If that fails**, the security suite is switched to the image's
main archive (`archive.ubuntu.com`, the first `URIs:` of `/etc/apt/sources.list.d/ubuntu.sources`), and the install
runs again. The main archive carries the same `resolute-security` updates. The build log says when this happened
(«F10: security.ubuntu.com failed; …»). Nothing changes when security.ubuntu.com answers.

## How verified
- In a bare `ubuntu:26.04` container: after the switch, both `URIs:` lines are archive.ubuntu.com and
  `apt-cache policy libtiff6` offers the security version (4.7.0-3ubuntu5.1).
- The amd64 and arm64 26.04 images both name archive.ubuntu.com first.
- A full local build of the image with the new step.
- CI's three image builds on the pull request.
